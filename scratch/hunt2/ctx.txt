HUNT II BRIEF: THE ENGINE FAILS A DIFFERENTIAL FUZZ AGAINST A MODEL (read it completely; it binds you).

THE PROJECT. supdb (/home/user/supdb) is a read-optimized embedded key-multivalue store; bench/ is its suite against LMDB and RocksDB. Read /home/user/supdb/CLAUDE.md first (the same file is in your worktree): the invariants and the "Shapes the bugs come in" entries are real, each cost a gate cycle, and most of what follows is a member of one family or another: read every entry about merges, promotions, pieces, fences, tombstones, seals, publishes, tilings and the segment work before you read any code.

WHAT WAS FOUND. The reviewer of the second form's branch wrote a 2,187-line differential fuzz (/tmp/claude-0/-home-user-supdb/43547e2e-b745-59c0-b3a0-b32f7c7e7919/scratchpad/wave2/review-inv/keep/zreview.rs, with fuzzrun.sh, crun.sh and mkbase.py; mkbase.py rewrites it to run against an engine WITHOUT the second form, i.e. the current head of the parent branch; read mkbase.py first). It holds the engine to a model of keys and values through the writer, claimed handles (Latest and Snapshot), fresh handles, and across puts, multi-value keys, deletes, seals, flushes, merges, promotions, ordered bursts that become direct runs with commit markers, clean closes and crashes, with the upkeep and the segment work inline or on threads, and random Options (tiny partitions and seals, inline limits, compact records, promotion, sync policy). Run against the engine WITHOUT the second form, at 5-10% of its seeds it found, by the reviewer's own account (not verified by anyone else):
 (1) Db::append(b"", v) as the first write of a fresh memtable panics 'memtable arena: an offset past what was published' -- ALREADY FIXED on branch fix-emptykey (commit e2e1301): do not touch it; the fuzz should not generate the empty key first until your base has it (merge fix-emptykey into your branch if you want to).
 (2) commit/flush/settle return 'compaction would write a key outside its fence', after which the store reports 'the store's segment work has stopped' (6 of the first 60 seeds; with partition_bytes 4 KiB, seal_bytes 8 KiB and values up to 700 bytes in the other reviewer's run).
 (3) the debug_assert in publish_segs_with, 'a segment publish left partitions that do not tile the key space', kills the maintenance thread, after which the writer sometimes parks forever in land_seal (seed 38 in the reviewer's damage mode timed out at 600 s).
 (4) RAW SCANS RETURN WRONG ANSWERS with the block cache off: values out of append order, a duplicated value, a deleted key listed (the reviewer's seeds 36, 40, 322; and 665 with the block cache on).
 (5) with the block cache on: panic 'a copy from the form disagrees with the build from the sources'. (Two more block-cache-on defects, a Snapshot handle's scan returning a write made after it and the cut_known assertion, are owned by another hunt running now; do not chase block-cache-on failures unless they reproduce with the cache OFF.)
These are in the shipping engine. A store that returns a wrong value, or stops its segment work, or hangs, is the worst thing this project can ship, and it is exactly what a clean test result hides ("A clean test result proves nothing about a path the test never took"). The aim of this campaign is to leave the engine unable to fail the fuzz at any seed in a long run.
