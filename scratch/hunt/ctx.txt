HUNT BRIEF: A SNAPSHOT HANDLE READS A WRITE MADE AFTER IT (read it completely; it binds you).

THE PROJECT. supdb (/home/user/supdb) is a read-optimized embedded key-multivalue store; bench/ is its suite against LMDB and RocksDB. Read /home/user/supdb/CLAUDE.md first (the same file is in your worktree): the invariants (especially "Two publishers, one pointer, and nothing a reader follows moves" and "The writer's upkeep is lent, never shared") and the "Shapes the bugs come in" entries are real, each cost a gate cycle, and this bug is very likely a member of that family: read every entry about marks, carries, forms, snapshots, handles, tables, looks and publishes before you read any code.

THE BUG. Found by the stage-2a build agent of the second form while it made tests reliable; it exists without the second form. With the block cache on (Options::scan_block_cache, on by default), a Snapshot handle (Reader::snapshot() after Db::reader()) whose FIRST scans come after a settled start returned a write made AFTER the snapshot, for a key that was already unsealed (a point read through the same handle was right): about 1 run in 200 (8 of 1,300 on wave2-base's engine with the second form off; 2 of 600 with it forced). A second, probably related defect: with the block cache on, in the checked profile (debug assertions on), the forms upkeep thread's debug_assert in BuildCtx::cut_known, "an overlay key's cut is behind the walk" (src/db.rs, search for it), fires about 3% of runs (6 of 200 on wave2-base) of the same oracle workload, and then Lend::take_back's debug_assert "the writer's upkeep is lent" panics again inside Drop for Db while unwinding, and the process aborts. 0 of 200 with scan_block_cache off. A throwaway patch that bounded the handle's adoption of a published scan snapshot by its own log position did NOT move the first defect: the cause is not known, and nobody has an explanation that a test has confirmed.

THE REPRODUCER (not minimal, not deterministic): the branch wave2-zproof of the shared repository carries the test that exposed it at commit dabf8d0: git show dabf8d0:tests/zpages.rs, test scans_agree_with_the_model_over_every_window_of_a_covered_store (its helpers are in the same file; it uses the second form, which you can drop: the form is derived data and only changes which pages a scan reads). Shape: Db::create with partition_bytes about 160 KiB and scan_block_cache on; an ordered load of 5,000 keys and a flush; hold_seal_landing(true); three rounds of 120 random operations (put, delete, append a key between records) each committed, a seal after the second so the first two rounds sit in a frozen table; scans of every window (start at fence keys and a byte either side, limits 1..usize::MAX) through the writer and through a Latest handle held since before the rounds; THEN snap = db.reader(); snap.snapshot(); the writer puts 200 keys again and commits; the snapshot handle's scans must answer the model as it was at the snapshot. The failure: a scan through snap returned the 'after the snapshot' value for a key. The oracle workload for the second defect is tests/zpages.rs on wave2-zproof (the test with 'oracle' in its name, run with scan_block_cache on).

WHERE TO LOOK, WITHOUT BEING TOLD THE ANSWER. src/db.rs: Reader::snapshot, the pin of a handle (state, mark, the three quantities of a mark), Reader::scan and the block-cache path (scan_blocks, BlockTable, refresh_snapshot, the scan snapshot and its adoption, install_ahead and the builder ahead), State::forms and the published forms (CanonicalForm, publish_form, carry_published), Reader::rebase_tables and State::replaced, the upkeep thread's pass (upkeep_pass, the lend and take-back), cut_known and the cuts, settle_each. A published form is current to a log position; a handle at an older position must not read it, and a form is mutated in place by a patch in more than one place. Candidates are worthless until a schedule that forces one has been run and has failed deterministically.
