## 5. Behaviour changes (what a caller now sees; each a yes/no for the owner)

1. A commit whose log write the device refuses answers Err. Its batch stays staged and is written, and made visible, by the next commit with that commit's batch. An Err commit is "not yet", not "never".
2. After a failed fdatasync or fsync of the log, of a closed log file, or of the log's directory, every commit (a transaction's included), sync, flush and seal answers Err until the store is reopened, in words naming the reopen; `close` answers it too and seals nothing (a_failed_log_sync_is_kept_until_the_store_is_reopened). Reads go on. The same holds for a log write that cannot be cut back. Before, the next commit could answer Ok. The answers after the first are new errors of the same kind with the cause's text in them (`lost_answer`, src/db.rs:4352): `raw_os_error()` is gone from them. (corrected: transaction and close added; missed: the error's errno)
3. A failure of a sync (EIO, or ENOSPC reported by an fdatasync), or a log write whose stray bytes cannot be cut back, now stops writes until a reopen, with no retry. A refused log or run write that is put back is not kept: it is answered once and written again by the next commit (behaviour 1, 4). (corrected: was "ENOSPC on the cut-back, one EIO ... There is no retry"; writes are retried)
4. In an ordered (direct) run, a refused or short write answers Err and the batch is owed. The next commit, a commit with nothing new, sync or flush now writes it again and fdatasyncs, whatever the policy. Before, a commit with nothing new and a sync answered Ok without I/O, and a commit after a partial write landed past the stray bytes, lost to the recovery walk (CLAUDE.md). (corrected: was "the last two", which named the sync and the flush; what a flush did before was not checked)
5. A failed fdatasync of a run's file, the writer's or the helper thread's, answers Err from then on until reopen. Every later write to the run is refused. Its close cannot finish, so the seal queue stops.
6. Under SyncPolicy::Always, a commit can now answer Err for a failure the helper thread met behind the writer. Before, it answered Ok.
7. Db::delete now raises the store's greatest key. A later append of a key between the old greatest and a key deleted above it goes through the log, not a direct run.
8. After a reopen that replayed log frames, the first sync issues fdatasyncs of the replayed files, oldest first, and the first flush is answered only after its slot's fdatasync. Before, both counted the replayed frames as synced.
9. An open finds a log file whose first sector is zeroes: newest, or older before a loose boundary, it opens as empty and the frames behind the zeroes are dropped. Before, every open refused with "not a supdb WAL". Before a chained file, or with zero header bytes over a non-zero sector, it refuses as damage.
10. Under EveryN with an ordered run open, Db::sync now writes the run's held tail and fdatasyncs the run's file, and syncs the log whatever table is live. Before, it did neither. The buffered bench arms' closing sync now pays this.
11. A seal that fails at any step stops the seal queue until reopen. Every flush and settle answers Err, and so does every call that must land a seal: inline, every seal and every commit at the threshold; in the background, once the frozen tables are full. The log is never retired, so it grows. Merges finish and are held, and their outputs are swept at the next open. Before, a seal that failed after its readable landing (data fsync, directory fsync, envelope, joined presync) let the store go on and a later manifest named the failed segment; one that failed before it already stopped the queue. (corrected: "before" holds of the after-publish failures only)
12. After a failed presync of a run's records, every later flush answers Err until reopen. Before, the next flush answered Ok (tests/db.rs a_failed_presync_is_the_flushs_answer was restated).
13. Behind a stopped queue with no room, a write that ends an ordered run, or the first write after a sync handed the live table (adaptive_shape), is dropped. From then on every commit, sync and flush answers Err until reopen. Before, the write that ends a run panicked in the ordered table's order check; the write after a hand-off was dropped already, answered once by the next commit, and the commits after it answered Ok over it (CLAUDE.md, "A refusal that came after the take"). With room in the frozen list both writes are taken (a_write_that_ends_a_run_over_a_stopped_queue_with_room_is_taken, a_write_after_a_hand_off_over_a_stopped_queue_with_room_is_taken). (corrected: "Before, that write panicked" was true of the run-ending write only)
14. A drain's run segment now lands durable only after the writer's presync, and a merge finishing in that window waits. Timing only; unpriced (drain-order).
15. Manifest slots: two publishes with no returned fdatasync between them write the same slot. Before, they alternated by parity. Any outside tool that read the slots by parity now reads them differently.
16. Every Db::open now fdatasyncs the slot it takes: one open(2), one fdatasync and one close(2). A failure fails the open and leaves the directory as found.
17. Db::open now refuses, with every file left in place, where it used to answer Ok after deleting files, or to fail with a bare NotFound after deleting: (a) no readable slot beside par-/pcs- files or envelopes ("refused: no manifest slot can be read, beside <name>, which only a store with a manifest writes; nothing was removed", and the envelopes' variant); (b) a slot naming a file that is not on the device ("refused: the manifest slot <slot> names <name>, which is missing from the directory; nothing was removed"); (c) in the clear, an unnamed merge or run segment within the slot's coverage whose last key nothing named holds ("refused: the manifest slot <slot> is not the store: ...; nothing was removed") (Db::open_refusals, Db::unnamed_refusals). The log's refusals: a zero header over a first sector that holds anything else, "not a supdb WAL"; a zeroed older file before a chained one, "sequence gap". (words added)
18. Db::open stats every segment the slot names, replays the whole log before it removes anything, and under manifest_pending, with `manifest_slots` on and in the clear, fsyncs the adopted pending segments, their ordered indexes (under ord_durable) and the directory before it writes the durable slot; under the rename shape it fsyncs none of them (followup 55), and under a cipher none here (the envelope was synced before the pending slot). (corrected: the fsyncs are under `opts.manifest_slots` and `held.is_none()`)
19. Under manifest_pending, the close writes no slot over a stopped queue, and the pending slot stays.
20. SegmentWriter (public, write-once callers): sync now answers a helper's failed fdatasync on every later call, and refuses later writes. Writes go to the offset the writer counts (pwritev), not the file cursor.

## 6. Owner items (decide; what each choice costs)

1. The kept error, until reopen (behaviour 2-5). It is kept for a failed sync (log, loose file, log directory, run file, helper) and for a log write that cannot be cut back; a refused write that is put back is already retried by the next commit (the batch_from CRC shape, built in 0aa41df7; the run's owed batch in 38378d1d). So the decision left is about syncs alone: accepting it means one EIO or ENOSPC reported by an fdatasync stops the writer until the caller reopens; retrying a sync is not an option, because of errseq. (corrected: the write retry was offered as the alternative and is what the units built) Cost when nothing fails: none, per the count, apart from the item-4 regressions.
2. Seal queue stopped until reopen, merges included (behaviour 11-13). Accepting it means the log grows and every flush answers Err until reopen. The alternative is "a store that goes on" (ROADMAP): reseal into a new inode, unbuilt. Also decide whether a sync should answer a stopped queue by itself (a writer-side kept answer; ROADMAP). Today a caller that only syncs learns nothing until a write is dropped.
3. A zeroed first sector with frames behind it (followup 2). Within the crash model those frames were never synced, so they are cut. Media damage to a synced first sector reads the same and loses acknowledged frames silently. Choices: keep the cut, or set the file aside where a commit frame behind the sector verifies (plain log only; a sealed log cannot verify without its header).
4. Opens that now refuse damaged stores (behaviour 17). Before, those stores opened Ok with data deleted, so the refusal is safer. But a store damaged on disk today stops opening, and nothing repairs it. The residue still opens silently: a fall back past a damaged slot whose log retired, and under a cipher the fallback that sweeps envelopes (ROADMAP; media damage only; followup 41). Closing it needs a format change (the slot names its log file).
5. errseq across a reopen (followups 33 and 49). Choices: docs only (engine-tidy's plan), or build the remedies: read the slots past the page cache, and rewrite replayed frames into fresh pages (a new log file, or a seal of what was replayed). The second costs one write of the replayed tail at an open after a failure. Testing it needs a dm-flakey device in the CI job that has sudo.
6. The shared log/run sequence (decision 1, taken). It is not scheduled in the next run. Waiting on it: run-tail-kill's power-cut sibling, and repairing stores written before f8d130a8 that hold a run of a deleted key (those open with the appended values masked). Cost: a format and recovery change, ~8 bytes a run marker, its own crash tests.
7. The pricing run's verdicts (run-close, due-log, run-dir, helper-race, drain-order, open-cost). Each verdict either takes a priced write, syscall or wait on a success path, or leaves the hole as a documented exception. In the crate docs today: SyncPolicy and Db::sync name the closed-run exception, and SyncPolicy names the due-commit window.
8. Success-path regressions the count found (concerns 2-4). Accept them and correct CLAUDE.md's "pays nothing" sentences, or give them a tidy unit (none has one). The largest is +4 instructions a key on an ordered run's commit.
9. The manifest_pending arm (supdb-manifestpending): the report asked whether to fix it or remove it. Stage 0 fixed it; followups 29 and 55 remain. Keep it, and the open fsyncs a pending set under every slot shape (engine-tidy, item 55). Or remove the arm and drop that work.
10. Root and privilege. A slot-choice test passes without root, printing "not run" (followup 28, tests-tidy). Real device faults need root and a loop device. Decide whether CI's sudo job runs a dm-flakey suite, and whether the gate fails when it did not run.
