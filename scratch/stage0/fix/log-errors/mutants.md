## Survivors

- **Sd** (the kept error cleared by the next successful fdatasync): equivalent. Every path to `sync_wal` (commit, commit_staged, seal, `Db::sync` through commit_staged, `log_run` through commit_direct) passes a `pending_err` check first, and that check refuses while an error is kept, so no fdatasync is issued after a kept error in the store's life and the added line never runs. Nothing to test; the mutant adds code, there is no check to take out.
- **O5** (`get_or_insert` swapped for `insert`, so a later kept error replaces the first): equivalent today for the same reason -- a second `keep_lost` cannot happen in one life, since every keep site is behind the same refusal. Kept as `get_or_insert` because the next unit adds keep sites on the direct run's path (`run-write-fail`), where the first error must win; that unit's tests are what can hold it.
- **O6** (`chain()` moved after the live file's fdatasync): not on a line this unit changed (the order of `chain` and the sync is the existing code's; the unit only restructured the sync's error path beside it). It survives because no test holds that the header byte a loose file's chaining rewrites is synced by the sync after it. A test would need a seam that drops the header's unsynced write at a power cut; it belongs to the open-time units (wal-fresh-header / replayed-marked-synced), and is reported, not added.

### Survivors (round 2)

### Survivors (round 3)

- **R5**: the mutant differs from the shipped code only when the error `answer_pending` takes is not the kept answer while one is kept. Every writer of `pending_err` but one uses `get_or_insert` or the `is_none` guard (`writes_go`, `rotate_wal_by_size`, the seal's rotation, `keep_lost`), so none displaces a kept answer; the one that overwrites is `leave_direct`'s `self.pending_err = Some(e)` when a run's close fails. A test was built for it (a cipher run kept by a failed sync, a held seal whose landing is then failed with `fail_next_landing`, and a write below the greatest that leaves the run): the run's close fails at `land_seal` as intended, and the write that ended the run then panics -- `put` and `delete` at `MemTable::put`/`delete`'s "never reaches an ordered memtable" assert, `append` at `write`'s "an ordered memtable takes each key above its last" debug assert -- because a failed `close_direct` returns before `set_mem` and leaves the ordered table live. That is a defect of its own, present at 3df85d22 (`leave_direct`'s overwrite and close are unchanged by this unit), and the state that tells R5 apart lies only behind it. The test was taken out; the defect is reported. The shipped re-arm (whenever `lost` stands, whatever was taken) is the simpler and the sound one; no check is there to take out.
- **R7** (= X3): equivalent; see round 2. The one-shot it would overwrite can only be one set before the keep inside the same call, and losing it in favour of the kept answer changes which refusal the next call reads, not whether it refuses.
- **R9** (= E10): equivalent; see round 1. `loose_wals` is read only on paths behind the kept refusal, and is not on disk.
