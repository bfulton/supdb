THE OWNER'S GOAL THIS SERVES: an encryption feature that is reliable, performant and not fragile to maintain, in which form changes are easy without constant encryption changes. The seal (unit G1-7, commit 41a07cf6; forms.md R2) is two things. The compiler's half is the seal: a whole borrow of the read path takes a zero-sized token whose constructor only its reader can call. The text half, tests/source.rs's seal_check, holds what the compiler cannot see: a token's module growing a second way to make one, a token made apart from its call, a new caller inside a reader's own module. The stage's closing critic read the text half and found it trips on ordinary code (scratch/plan/build/close/g1-built.md, "Concerns" 4 and "Owner items" 1; read both, and the unit's notes scratch/plan/build/G1-7/notes.md):
- the words `lent` and `lend` are refused anywhere inside any macro's tokens, and they are common words in this engine (the upkeep has a field `to.lent`, src/db.rs has a local `lend`), so `debug_assert!(to.lent <= n)` in new engine code is red; four test assertions are excepted in SEAL_MACRO_WORDS by file, scope and exact text;
- SEAL_DECLS and SEAL_MACRO_WORDS are keyed by a line's exact text, so rustfmt rewrapping a listed line (a signature that grows past the width and splits) or a renamed test function turns the gate red for nothing;
- any `.base(x)` or `::base(x)` call with an argument anywhere in src reads as the seal's `base`;
- the failure message names the list to add to and not what the author is to do.
The critic recommended, and the launcher decided: give the seal's words names nothing else in the tree uses, and read each word wherever it stands.

HOW TO WAIT. An agent never ends its turn to wait for anything: a turn that ends is taken as the step's answer, at once, with whatever is unfinished reported as unfinished. A command that outlasts one call is started in the background with its output and its exit status in a log ("...; echo EXIT $? >> log") and waited for in a foreground call: `until grep -q '^EXIT' <log>; do sleep 20; done; tail -5 <log>` with the call's timeout set to 600000, issued again each time it times out. A call that begins with a bare `sleep` is refused; the Monitor tool and a background wait both return at once, so neither is the way to wait, whatever another instruction of this launch says about Monitor. Before answering, kill what you started that still runs, put the tree back from your newest kept copy by sha256 if a mutant is in it, and say in the notes what remains.
