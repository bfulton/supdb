The stage's closing run found "sh scripts/check.sh cross-arm" (the library's unit tests built for aarch64 Linux and run under qemu-user, with --cfg supdb_emulated) dying in two parallel runs of five with a crash inside the emulator and no test failed:

WHAT THIS CHANGE IS. The crash found, and the group made to give a verdict, in that order. Not a retry, not a blanket --test-threads=1, not a guess.
1. Reproduce and measure, without cargo in the loop. Build the aarch64 test binary once with the group's own environment (read scripts/check.sh's cross-arm case; "cargo test --no-run" with the same three variables and the same profile and target gives the binary the group runs), then run that binary directly under "qemu-aarch64-static -L /usr/aarch64-linux-gnu" as many times as the measurement needs, each run's output and exit status in a log of its own. First the rate of the whole binary in parallel as the group runs it (at least ten runs), kept as before.log with a table in the notes.
2. Find what is in flight when it dies. The harness prints a test when it ends, so the last names printed are not the suspects. Instruments, cheapest first: qemu-user's own syscall trace ("qemu-aarch64-static -strace ...", every guest syscall with its thread, entry before the call and result after it, so a thread whose last line is an entry with no result names the syscall QEMU died inside; -D sends it to a file; it slows the run and may move the rate, so measure the rate under it); filters by module and then by test to find the smallest set that still dies, each candidate run enough times to tell a rate of two in five from none (ten clean runs of a set is weak, thirty is better: say what the count shows and what it does not); RUST_TEST_THREADS to see whether one test alone dies or it needs a neighbour; the eleven tests added since 19d078d1 as the first suspects ("git diff 19d078d1 HEAD --stat -- src" and the test lists of the two binaries, "--list", diffed). If gdb is installed, a core or an attach gives QEMU's own stack; the binary is stripped, so say what could and could not be read.
3. Say whose bug it is, with evidence, before anything is changed. The message means the host fault was in QEMU's own code. Two very different causes produce it, and the change depends on which:
   (i) QEMU's own defect on a legitimate sequence of guest syscalls (qemu-user emulates mmap, munmap, mremap, madvise, mincore, membarrier, /proc/self/maps and friends itself, with its own page tables and locks, and 8.2 has known races there). Evidence: the syscall and the concurrent syscalls of the other threads from the trace; the same arguments shown to be ones the program is entitled to make (a range it mapped itself, a file it opened); and, where it can be done in an hour, a reproducer with no engine in it (a few threads making the same calls, built for aarch64, run under the same qemu) that dies the same way, kept under the change's directory with its command.
   (ii) the program doing something it is not entitled to that a real kernel forgives or hides: an munmap, madvise or mprotect of a range it does not own, a mapping used after it was unmapped, a length past the mapping. Under qemu-user the guest and the emulator share one address space, so a wild range can land on the emulator's own memory. That would be a real defect of the engine or of a test, on every platform, and the change is then its fix, with a failing test first on the native target if one can be written (a debug assertion on the range, a test that reads /proc/self/maps before and after), the count against the commit this began at for any compiled engine code (scripts/cost.sh, by function, every probe the function is in), the stride group, and the mutants on the lines of the fix.
   Do not decide between them by the message or by which is more convenient: the trace's arguments against the mappings the program made (its own mmap results in the same trace) decide.
4. Make the group give a verdict. For cause (i), in this order of preference, taking the first that the evidence supports:
   (a) the smallest set of tests that drive QEMU into its defect compiled out of the emulated run alone (#[cfg(not(supdb_emulated))], beside the cfgs the test already has), each with a doc line in the manner of the six that are there now (grep supdb_emulated src: "Not under qemu-user (supdb_emulated), which ...") naming what QEMU cannot run, and the notes showing by the two binaries' --list that exactly those names left and that the native runs (the test group here, the native ARM leg in CI) still run them. A test kept out is a path the emulated run no longer covers: say for each what ARM-specific code it was the only emulated cover of, if any (the CRC and prefetch paths are what the job exists for);
   (b) if the defect is reached by any two tests of a kind (every test that maps and unmaps beside another thread, say) so that (a) would empty the run, the group runs those modules one test at a time and the rest in parallel, in scripts/check.sh's cross-arm case and nowhere else, with the reason in the comment above the case; the CI job stays "sh scripts/check.sh cross-arm" with nothing else in the YAML (tests/source.rs holds the workflows to that; read its fixtures before editing the case, and add a red case if the check's reading of the case's text has to change);
   (c) only if neither can be shown: the whole group one test at a time, with the wall time said and the reason.
   A newer QEMU is not an answer: the runner's is the one apt gives.
5. Docs: scripts/check.sh's comment on the group says what is compiled out and why, as it does now; CLAUDE.md gets a rule only if this taught one, with the failure that taught it, in that file's manner (a test compiled out under an emulator, or a crash of the instrument read as the program's or the other way round); scratch/ is not edited.

RUNNING THINGS. One heavy thing at a time: a run of the test binary under QEMU uses every core for minutes, so runs are sequential, never beside a cargo build or another run, and the long loops go in the background with a log per run. The aarch64 target directory is about half a gigabyte; the cross toolchain and qemu-user-static are installed (the closing run used them); if either is missing, "apt-get install gcc-aarch64-linux-gnu qemu-user-static" and "rustup target add aarch64-unknown-linux-gnu" are how they came. Each run gets TMPDIR under this change's directory, spelled canonically, removed by its literal path between batches: a run that dies leaves its stores behind, and thirty dead runs fill the disk.

HOW REVIEWERS READ IT. The claim to attack is point 3's verdict. Read the trace lines the notes quote against the trace itself (it is kept): is the range in the dying call one the same thread or another mapped, is another thread unmapping or remapping it at that moment, could the program's own call be wrong (a length past the file, a range freed already)? If the verdict is (i), try to explain the crash as (ii) and say what observation rules that out; if (ii), the reverse. Then the arithmetic of A. Then whether each test kept out is shown to matter.

HOW TO WAIT. An agent never ends its turn to wait for anything: a turn that ends is taken as the step's answer, at once, with whatever is unfinished reported as unfinished. A command that outlasts one call is started in the background with its output and its exit status in a log ("...; echo EXIT $? >> log") and waited for in a foreground call: `until grep -q '^EXIT' <log>; do sleep 20; done; tail -5 <log>` with the call's timeout set to 600000, issued again each time it times out. A call that begins with a bare `sleep` is refused; the Monitor tool and a background wait both return at once, so neither is the way to wait, whatever another instruction of this launch says about Monitor. Before answering, kill what you started that still runs, put the tree back from your newest kept copy by sha256 if a mutant is in it, and say in the notes what remains.
