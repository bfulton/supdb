# G-wall: the forms and the encryption modules do not name each other

Scouting notes for rule R0 and the gate test G-wall of `seam/forms.md`.
Read only, from the export of commit 682b2c09 at `plan/tree`. Nothing was
built or run. Paths below are relative to the export's root unless they
start with `plan/` (meaning
`/tmp/claude-0/-home-user-supdb/2fecfb3d-3630-50b2-b9c5-2a19705f39b6/scratchpad/plan/`).

## 0. What decides the work

1. `src/db.rs` cannot be judged per file. It holds 232 code occurrences of
   the final cipher vocabulary (section 2.4) in 88 enclosing scopes
   (`wc_dbfns.tsv`; 151 ratchet lines once top-level items are keyed by name). 134 of the 253 on
   the form side are plumbing that stays (the mode enum, the open, the
   handle's `ATTN_PAGED` bit, the rests, the pager wiring). The test must key
   counts by enclosing function. That needs a small Rust lexer in the test.
   My Python prototype of one needed seven fixes before its brace depth closed
   at zero in every file (section 5.4). The lexer is the risk.
2. The ratchet can start today. The draft file `plan/wall/couplings.txt` has
   233 data lines and was generated by `plan/wall/gen.py`. The red input
   (`super::vault::kept(path)` added in `zfile::warm_file`) shows up as a new
   key (section 5.6).
3. Two of the stage assignments rest on plans that disagree with each other
   (section 4.3). The envelope arm's form knowledge (74 vault.rs occurrences,
   plus 9 in db.rs and zfile.rs) is said to go "at S3" in design.md section 6.
   But design.md section 10 keeps the envelope arm alive past S6
   (`supdb-cipherenv` "until it is deleted"). No stage deletes it. The S6
   lines (`LogCipher`, `passes`, `seal_manifest`) have the same problem if
   the envelope arm keeps its sealed log after the flip.
4. `forms.md` B lists `Kind` as a token. It is a private enum of vault.rs
   (`enum Kind`, vault.rs:468), so the compiler already keeps it out of form
   code. It is counted on the encryption side instead (`Kind::Seg/Ord/Form`).

### 1.2 How a test over one file tells plumbing from coupling

| choice | how | cost to keep true |
|---|---|---|
| **A. Ratchet keyed by function** (recommended) | every count is keyed by (file, enclosing scope, token, region). Plumbing lines carry stage `stays` | needs a lexer that finds scopes (section 5.4). A rename or a move of a function is a one-line edit of `couplings.txt`, and the failure names both keys. Growth inside plumbing is still red, so a new cipher branch in `Db::open` needs a line edit and review |
| B. Marked regions (`// wall: plumbing` ... `// wall: end`) | lines between markers are skipped | about 30 regions in db.rs (the read path alone is spread over db.rs:19069-35133). New code typed inside a region escapes. An edit can move a marker silently. Rejected |
| C. Allow-list of function names, no counts | listed functions may say anything | Growth inside `Db::open` or the `Reader` read path is invisible. That is where the next cipher branch would be added. Weaker than A at the same lexer cost |
| D. Move the plumbing out of db.rs | the wall becomes per file | the end state. `impl Reader` blocks can live in a child module such as `src/db/pin.rs`, since a child module sees its parent's private items. The pin rename at S1 is the natural moment for the rest and `unlent` family. The open's mode match is interleaved with 600 lines of open (db.rs:28684-29364) and does not move cheaply. Not for G1. Changes no codegen in principle, but callgrind rows 1-2 would be re-run (not verified) |

Recommendation: A at G1, with D as the direction. Under A the "allow-list" is
simply the `stays` lines of the same file. That costs nothing extra and also
holds plumbing to its count.

## 2. The cipher vocabulary on the form side

### 2.1 Method

Tools, all under `plan/wall/`:
- `lex.py`: a lexer that splits each line into code text (string literals
  kept, comments removed) and comment text. It marks `#[cfg(test)]` /
  `#[cfg(all(test, ...))]` items and `#[test]` fns, and names the enclosing
  `Type::fn`.
- `count.py ROOT TOKENS.json OUT FILE...`: per file, token and region counts,
  plus a `.hits.tsv` with every site (file, line, region, scope, token, text).
- `gen.py TREE`: the draft ratchet.

Regions: `code` and `comment` outside tests; `tcode` and `tcomment` inside.
Each token is a Python regex, counted with `findall` per line. Tokens that
overlap (`cipher` inside `zpages_under_cipher`) are counted under each.

Form files scanned: `src/db/zfile.rs src/db/zpages.rs src/db/zselect.rs
src/db/zlz4.rs src/db/blocks.rs src/ordindex.rs src/flatindex.rs src/blob.rs
src/block.rs src/index.rs src/format.rs src/reserve.rs src/db.rs`, and
`src/wasmapi.rs` for the final tokens.

How hidden sites were covered:
- **Paths and imports.** `grep -nE '^\s*(pub(\([a-z]+\))? )?use '` over the
  form files and db.rs found no `use` of `vault`, `pager`, `crypt` or
  `dirkey`, and no `as` alias of them. Form code reaches vault only as
  `super::vault::x` (zfile.rs, 15 sites) or `crate::db::vault::map`
  (ordindex.rs:404). A token `use of an encryption module`
  (`\buse\b[^;]*\b(vault|pager|crypt|dirkey)\b`) counts 0 on the form side
  and belongs in the test, so a future alias is red.
- **Methods.** I listed every `pub`/`pub(crate)` fn of vault.rs and pager.rs
  (`grep -nE '^\s*pub(\(crate\))? fn \w+'`). I then grepped db.rs code for
  `\.(adopt_all|log_begin|log_resume|open_manifest|seal_manifest|seal_into|open_records|sweep|vault|pager|breathe|breathe_unless|breathe_swamped|crowded|swamped|room_for|set_grace|held|backed|present_chunks|plain_len|could_give|nudge|oldest_lent)\s*\(`.
  The `.sweep(` hits on the retired lists are false positives; the rest
  became the `sealed log/manifest` and `vault/pager method` tokens.
  - A method called through a binding made earlier (`p.check()` at
    db.rs:28642, `p` bound from `shared.pager` one line up) is not counted.
    Its binding is. A new call through an existing binding in the same scope
    grows nothing. This is a known hole.
- **Macros.** There are 3 `macro_rules!` in blob.rs and 2 in wasmapi.rs.
  None of their bodies holds a token (no hit has a `name!` scope). Macro
  bodies are scanned as code.
- **Trait impls.** Traits are named by their header line: `impl pager::Grace
  for PagerGrace` (db.rs:10388), `impl MergeRest for &pager::Hold`
  (db.rs:12818), `impl Walked for Held` (zfile.rs:4544).
- **Raw strings and raw identifiers.** `grep -rn 'r#"'` and `'\br#[a-z]'`
  over `src/` find none. The lexer still handles them.

### 3.2 What each coupling does (vault.rs, code)

- **The kinds and their names.** `enum Kind { Seg, Ord, Form }`
  (vault.rs:468). `Kind::suffix` (479) and `disk_parse` (521) map `x-<token>`,
  `.o` and `.z`. These are the stored names of a segment, its ordered index
  and its form file. 10 occurrences.
- **The companion cascade.** `Vault::remove` (981) removes a segment's `.z`
  with it (2). `Vault::companion` (1489) and free `companion` (2188) learn of
  a form file beside a segment (11). `Vault::persist_form` (1425) and free
  `persist_form` (2146) write a form's envelope under its segment's token and
  key (12).
- **Segments with their ordered index.**
  - `Vault::persist_with` (1299, 13) writes a segment's envelope and then its
    `.o` under the same key.
  - `persist_one` (2129, 6) calls `crate::db::Db::ord_name_for(seg)`. This is
    the one code site where vault names the engine.
  - `Vault::adopt` / `adopt_all` (1527, 1575; 18) take (segment, ordered
    index) pairs from the manifest.
- **The sweep's rule by kind.** `Vault::sweep` (1593, 2): a `.z` is held by
  its segment's token as well as by its own name.
- **Passing by name.** `passes` (562, 3) lets `wal-`, `spare-` and
  `manifest*` through to the directory. The count of 3 understates it. `passes(`
  is called 22 times in vault.rs code (`\bpasses\(` gives 23 with the
  definition), in `Vault::names` and 19 door verbs, each a branch that sends
  the log and the manifest to the plain directory. The proposal is to add
  `\bpasses\(` to the encryption-side tokens, starting at 23, to fall at S6.
- **The sealed manifest.** `Vault::seal_manifest` (1633), `open_manifest`
  (1657) and `slot_aad` (`b"manifest"`, 1755): 13 occurrences. They hold the

## 5. The test

### 5.1 Where it lives

`tests/wall.rs`, an integration test, reading files at run time from
`env!("CARGO_MANIFEST_DIR")`, as `tests/crypt.rs:340` reads `tests/data`.
Not beside `the_engine_names_no_file_but_through_the_door` (vault.rs:2876),
because:
- vault's test module is `#[cfg(all(test, target_os = "linux"))]`
  (vault.rs:2231), so the wall would not run on a non-Linux leg
  (`.github/workflows/apple-silicon.yml` exists; whether it runs the tests
  is not verified);
- the wall is a property of all of `src/`. A test inside one side's module
  is itself a coupling: that test already pins ordindex.rs's text
  (vault.rs:2902-2904);
- G-door replaces that test at G1 anyway (forms.md B).

`scripts/check.sh test` then runs it with the rest. It needs no cipher, no
store and no Linux, and takes seconds.

### 5.2 `tests/data/couplings.txt`

Tab-separated. `#` starts a comment line. Columns:

| column | value |
|---|---|
| file | crate-relative path |
| scope | `Type::fn`, `fn`, `outer>inner` for a nested fn, `Type::<item>` for a type body or impl header, `const NAME` / `struct NAME` / `mod NAME` for a top-level item |
| token | the token class's name from the test's own list |
| region | `code` or `test` |
| count | occurrences |
| stage | G1, S1, R4, S3*, S4, G3, S5, S6, or `stays` |
| reason | free text |

A draft for today's tree is `plan/wall/couplings.txt` (233 lines, plus
comment lines). The side is not a column: the test holds the file lists, and
section 1's table is the proposal.

### 5.3 Semantics

- **Measuring.** For every file in the form list, count the cipher tokens.
  For every file in the encryption list, count the form tokens. Key by
  (file, scope, token, region).
- **Growth.** A key measured above its listed count, or a key measured and
  not listed, fails. The message is `src/db/zfile.rs warm_file
  vault::<not a door verb> code: 1 > 0`, with each hit's line and text.
- **Shrinkage.** A listed count above the measurement, including a listed
  key now measured at 0, fails with `... 0 < 1: lower tests/data/couplings.txt
  (stage S3*)`. This makes the commit that removes a coupling lower the file
  in the same commit, as forms.md B requires.
- **Unclassified files.** Any `src/**/*.rs` not in a list fails.
- **Printing.** `SUPDB_WALL_PRINT=1` prints the measured table in the file's
  format to stderr. The test never writes the file, because a writer would
  make raising a count silent.
- **"Only goes down" across commits** is not visible to a test, which sees
  one tree. Two options:
  - CODEOWNERS on `tests/data/couplings.txt` (forms.md section 6);
  - a CI step that compares the file at the merge base and at the head per
    key (`git show origin/main:tests/data/couplings.txt`) and fails on any
    increase unless the line's reason changed. This is a script for the CI
    job, not part of the test. Not designed further here.
- **Comments are not counted.** A comment never makes a store wrong. Gating
  comments would push authors to delete explanations rather than couplings.
  The cost: 124 db.rs comment mentions of `cipher` can go stale as code
  leaves. A later stage could add a per-file comment ratchet. Its counts are
  in 2.4 and 3.1.
- **String literals are counted as code.** vault's names (`"wal-"`, `".z"`)
  and zfile's error message are what they couple by.
- **Test code is counted, in its own region.** A cipher test written inside a
  form module would break forms.md's (N). The form side starts at 10
  (db.rs `cipher_looks`), the encryption side at 270.

### 5.4 The lexer the test needs, and the traps found while prototyping

`plan/wall/lex.py` is a working reference, about 220 lines of Python. Its
self-check: every file's braces close at depth 0, and so do its
parentheses and brackets, outside strings, comments, char literals and
attributes. The check passed for all 20 files after these fixes, each of
which was a wrong count before it:

1. `#[cfg(test)]` on a struct field ends at the field's `,`, not at a `;` or
   `{`. Without this, zfile.rs's `ZFile::attach` was read as a test
   (zfile.rs:1949-1950).
2. `#[cfg(all(test, target_os = "linux"))]` has a comma inside the attribute.
   Attributes must be blanked before scanning. Without this, vault.rs's whole
   test module and db.rs's `mod cipher_looks` were read as code.
3. `[u8; WRAPPED]` in a signature (vault.rs:1527, 1686) is not the end of a
   declaration. A `;` counts only at bracket depth 0.
4. A string literal that spans lines (blob.rs:972, 2817; dirkey.rs:324).
   Strings must be blanked by the lexer, not per line.
5. A char literal holding a bracket or a brace (`'('`, `'{'`).
6. `-> impl Trait` in a signature is not an `impl` block. `impl` counts only
   at the start of a line.
7. `#[cfg(test)] if let ... { }` inside a fn (zfile.rs:2142-2146) is a test
   block, and the line after it is not.

A field-level `#[cfg(test)]` inside a struct literal nested in a call
(pager.rs:859) needs the bracket depth recorded at the attribute.

The Rust version should carry these seven as unit tests of its lexer, plus
the depth self-check over every file. Before the first commit it should be
cross-checked against `gen.py`'s output: the counts must be identical.

An alternative is `syn` (`full`, `visit`) with `proc-macro2`'s
`span-locations` for line numbers. Plain comments vanish in syn and doc
comments become attributes, which is convenient. String literals still need
a token walk. It adds the crate's second dev-dependency (only `ring` today,
Cargo.toml) and its compile time to the test group. Recommendation: the hand
lexer. The counting rules are defined by it either way, and CLAUDE.md
records the test group's compile time as a cost already paid down once.
