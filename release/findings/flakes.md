# The known flaky tests, before the flake loop

What this covers: the three flakes `release/history.md` ("CI at C0") and
`release/findings/guarantees.md` ("Found while gating phase 1") name, each
read from its hosted log first and then reproduced on this Linux VM by
choosing its phase. The tree is `98e4e8f4`, which is C0 plus the
coordinator's first merges, with `src/` and `tests/` as at C0 for every
file named here. No timing run was made.

A probe is a patch under `release/findings/flakes/` that applies to
`98e4e8f4` and adds a seam to one test, or a print, behind an environment
variable. The commands below run from a checkout at `98e4e8f4` with the
probe applied (`git apply release/findings/flakes/<probe>.diff`), and with
`TMPDIR` set to a directory of the run's own. `$B` is the test binary
`cargo test --profile checked --test <file> --no-run` names. "Busy" means
four `sh -c 'while :; do :; done'` loops on this four-CPU VM.

| `tests/durable.rs` `a_runs_commits_its_close_synced_before_a_due_one_outlive_older_log_frames` | **The test's premise.** The helper `run_tmp_name` took the first `direct-*.tmp` name the directory listing gave, on the reading that "an open run has taken the spare". But the writer reserves the next run's id when a run begins, and the segment work makes that file at the first landing after that syncs the directory (`Options::run_spare`). Here that landing is the hashed seal's readable landing, which races the run's commits. So the next run's file (empty, with a greater id) can be standing when the test names the run's file. The order of a small ext4 directory is the order of the names' hashes, which the filesystem's seed fixes: on some hosted runners the spare is listed first. tmpfs lists newest first, so it always is. Two shapes follow. (1) `tmp` and `ino` both name the spare. The lifter then waits for a link of the spare's inode that never comes: `the closed run's link: the case was not reached`, after 120 s (run 46050828621, `test` group). (2) The spare is made between `run_ino` and `run_tmp_name`, so `ino` names the run and `tmp` names the spare. The lifter's wait then passes at once on the run's own temp name, the copy is taken before the run closes, and the run's link lands between the copy and the loop: `remove_file` … `NotFound` at `tests/durable.rs:13918` (run 46057692113, `onefile` group, which only gives the binary a fresh `TMPDIR`). The same helper serves 25 other call sites. | With `durable-spare.diff`, `TMPDIR=/dev/shm/<own> PROBE_WAIT_SPARE=1 $B --exact a_runs_commits_its_close_synced_before_a_due_one_outlive_older_log_frames` fails with shape (1) every run (3 of 3). Without the probe the spare already stands at the naming in 2 of 6 runs on ext4 (`PROBE named` and the listing printed). Shape (2) needs the spare made between the two calls. The mis-pairing (`tmp` the spare, `ino` the run) was reached by putting the wait between them, in 1 of 8 runs; the `NotFound` itself was not forced. | **Fixed in the test.** `run_tmp_name` and `run_ino` take the store and pass over the next run's file where the store says it is made (`Db::run_spare_state` 2 or 4). That file has the greatest id of the temp names, and the helper holds it empty. The store's word is read on both sides of the listing, and the listing is taken again if the file was made inside it. The fix ran with the probe in place 6 times on tmpfs, the spare listed first each time: the run's file was named, and the test passed. The old helper fails the same probe (above). The whole `durable` binary is green on ext4. On tmpfs it fails the same 5 open-adoption tests at `98e4e8f4` with or without the fix: those 5 do not run on tmpfs and are not this flake. |
| `tests/settle.rs` `a_copys_identity_outlives_a_merge_that_kept_its_partitions_keys`, shape seen on hosted CI: `0 claimed, 0 of their partitions` (macOS, `stride` group, run 46050828621) | **Not resolved.** Every copy is gone after the merge. The same test shape in the sibling `a_copy_of_fixed_size_records_is_one_stream_until_a_write_it_cannot_take` failed on hosted x86 (run 46033466210, `onefile` group), and its message prints the drop counts: one drop by the upkeep's abandon (site 7, `Options::upkeep_abandons`), and two drops of the log read where the rebase refused (site 1, refusal 1). On this VM, holding the upkeep's pass pinned across the seals' and the merge's landings gives that same signature only when `upkeep_keep_bytes` is 1. With the default keep (an eighth of memory) no abandon fires here, and on macOS `zfile::read_budget` reads nothing, so the keep is unbounded there and the pin's abandon cannot fire. Which path dropped the copies on the hosted runners is still open. | With `settle-abandon.diff`, `PROBE_ABANDON=1 $B --exact a_copys_identity_outlives_a_merge_that_kept_its_partitions_keys --nocapture`: `0 claimed, 0 of their partitions`, drops at sites 1 and 7, refusal 1, every run. Without `upkeep_keep_bytes: 1` the same hold passes. 150 quiet-shaped runs and 180 busy runs of the test, six at a time, gave no `0, 0`. | **Proposal.** In phase 4, read the abandon's inputs on a hosted runner: `upkeep_abandons()`, `upkeep_abandon_state()` and the drop counts printed by this test's assertion, as the sibling's already prints them. Then decide between giving the two fixtures `upkeep_abandons: false` and a seam that holds the upkeep's look. `upkeep_abandons: false` alone was tried: with `upkeep_keep_bytes: 1` the copies are still dropped, at site 1. So it is not believed as a fix, and it is not committed. |
| The same test, a second shape found here: `11 claimed, 1 of their partitions` (the `by_keys` off arm, `SUPDB_TEST_STRIDE=1`) | **The test's premise.** The fixture `copies_of_records` writes three keys of four again. Under the stride switch, where form files serve, a partition of twenty keys then holds fifteen, a light form and not a copy (10 copies of 11 at the fixture's end). The upkeep converts that form to a copy whenever its pass comes, and the conversion yields to the writer. Where the pass comes after the merge's publish, the copy is built over the rewritten partition and rightly claims its key sequence. The test then reads it as a copy carried across. `copies_of_fixed_records` met this already, and writes seven of eight. | Busy, six at a time: 2 of 180 at `98e4e8f4`. Made wide with `settle-wide.diff` (the upkeep's pass held across the rounds until the merge has landed): `SUPDB_TEST_STRIDE=1 PROBE_WIDE=1 $B --exact a_copys_identity_outlives_a_merge_that_kept_its_partitions_keys` fails 5 of 5. | **Fixed in the test.** `copies_of_records` writes seven keys of eight, holds every partition to sixteen written keys, and asserts a copy of its partition's records in every partition at the fixture (`claimed == partitions`) instead of four. With the fix: the wide probe passes 5 of 5, and busy runs pass 240 of 240. `settle` is green under the plain, stride and onefile switches. |
| `tests/cipher.rs` `a_store_whose_cache_follows_its_room_holds_what_the_room_allows`, and the siblings `the_builders_rest_at_every_block_of_a_store_of_wide_values` and `the_compact_form_is_built_and_read_within_a_cache_the_store_does_not_fit` | **The bound is soft, and the test reads it as if the machine were quiet.** I did not judge this one as test or engine. A probe restarts the peak after the load, so the load's peak is ~4.8 MB quiet or busy, and the whole overshoot is in `holds()` (the point reads and the full scan). Quiet, that phase peaks at 3.5 MB; busy, at 4.6 to 9.3 MB, and 13.0 MB in the failing run (room + slack is 12.6 MB). Every thread's state was sampled every 2 ms across that 80 ms window. The test thread is always runnable. `supdb-maint` and `supdb-zbuild` still read through the cache, since `settle` returned before the merge and form builds were done. `supdb-pager` is runnable but off its core in 14 of 33 samples and in its `give` sleep (waiting out pins and holds) in 8. A reader past the swamp line waits one 20 ms breath (`Pager::breathe_swamped`) and reads on. So the overshoot is the readers' fill rate times the time the evictor, or a pinned reader it waits on, spends off its core. That is what `pager.rs` and `one_at_a_time`'s comment say the bound buys. The test's 8 MiB slack is a fixed allowance for it. | Busy, whole binary: `$B` failed `follows` in 1 of 6 runs here, with `held 12981344 of a room of four mebibytes … stalls: 257 … longest_wait_us: 230310`, and `the_compact_form_is_built_and_read_within_a_cache_the_store_does_not_fit` in 1 of 6. `the_builders_rest_…` passed 10 of 10 alone busy. With `cipher-phases.diff`, `$B --exact a_store_whose_cache_follows_its_room_holds_what_the_room_allows --nocapture` prints the peak of each phase. Thread states came from a sampler of `/proc/<pid>/task/*/{stat,wchan}` every 2 ms; it is not committed. The family appears on hosted CI too: `db::cipher_looks::a_close_that_joins_a_merge_holds_nothing_of_the_cache` (`src/db.rs:71695`, `stalls: 1191`) in runs 46096094960 and 46113676508. | **Diagnosis sent to the coordinator**, no fix written. The choices are (a) the engine, where a reader past the swamp line waits for the evictor and not only for a breath (a behaviour change, phase 1's); (b) `bench/DESIGN.md`, stating the overshoot under contention as the acceptable loss the comments already describe, with these tests reading the peak only with the machine to themselves, as `quick` does; or (c) the test, making the slack a function of the waits it counted (`breaths`, `waited_us`). |
